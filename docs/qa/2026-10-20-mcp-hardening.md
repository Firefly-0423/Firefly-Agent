## Product decisions left open

1. Establish a Main-owned credential form/vault and server-scoped secret references; remove credentials from model-authored install arguments; decide encrypted storage, command-line credentials, success-output redaction and child stderr policy together.
2. Decide whether destructive/write MCP operations require individual confirmation even under `full` or local effect overrides. Existing pinned permission modules remain unchanged.
3. Remediate and verify the failing OAuth issuer-binding dependency contract in an isolated, authorized dependency change; current production SSE has no OAuth provider wired in.
4. Choose an unambiguous tool namespace and migration for existing persisted overrides. Server and tool names currently have a concatenation collision.
5. Define complete MCP result rendering: text blocks currently win over embedded resources, and structured-only data is not substituted for `content` (`mcp-adapter.ts:323`). Changing output representation can affect model and user-visible results, so it was not included.
6. Define external metadata and compaction provenance beyond the added system rule, including legacy recovered tool messages. These must not silently acquire instruction authority.

## Review and threat model

The attacker considered is an approved but hostile/compromised MCP server, or content fetched from a page/issue, influencing returned text, error text and metadata. Concrete reproduced paths are: return a credential-bearing string to the adapter logger; reject a call with credential-bearing transport text; echo a configured env credential in `isError`; embed fake system/trust fields in tool content; fail after a possibly applied mutation while Harness ignores `no_retry`. Tests cover those paths using public synthetic strings; no live credentials or external commands are needed.

The review checked the entire working diff against HEAD. Adapter diagnostics and the catch-all semantic error classification originate in `22eba4f18`; connection ownership/cancellation was introduced by `38d60b578`, and catalog validation by `af9b97175` (`git blame` inspected). No ownership, cancellation, schema or approval checks were removed. Direct production call sites inspected: adapter connect has four (manager startup/add/enable and the device fixture); manager add has three (management IPC, installer and builtin sync); Harness prompt construction has one primary caller in run preparation; all five tool-result message call sites share the JSON boundary. Vendor wire adapters preserve tool-message content (`vendors/openai-adapter.ts:18`); recovery/closure code synthesizes host-owned unknown/not-executed notices (`harness/run-recovery.ts:64`, `conversation-transcript-context.ts:83`, `transcript-sink.ts:354`) rather than fetching another remote payload. Scope is surgical rather than an audit of every browser, plugin or vendor implementation.
