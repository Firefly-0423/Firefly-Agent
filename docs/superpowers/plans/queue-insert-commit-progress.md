## Codex 只读评审

共四次：方案、本 PR 范围、施工包 5 两轮，意见都已吸收。施工包 5 的两轮依次指出了：
- 先在读租约里提交历史、再在租约外写会话记录，中间有空档；
- 观察者先推进了版本号，写失败后本次运行补不上；
- 不可重试的错误让整批被拒，丢了前缀；
- 按错误码前缀判断能否重试不安全；
- 写入进度记得太晚，漏掉建目录失败；
- 撤销的承诺写得太宽。

## 未验证与已知限制

- 运行中会话记录写入失败（磁盘写满、文件被占用）没有在真机上造出来，只有测试里的故障注入；“写入丢失”只在真机上离线模拟过，见下文。
- 来源凭据只存在内存里：应用重启后，施工包 6 会补齐会话记录，但不会补发来源凭据；这类条目的默认记忆找回会被拒绝（不可重试）。
- 冲突、过期、授权失效都不重试，运行以“插话提交失败”结束，对外错误码是 `E_HARNESS_FAILURE`。
- 模型看到的中文固定说明、过程流里的气泡、页面接回运行，是后续 PR。

## 实机测试（2026-11-17）

环境：开发版（`npm start`），独立开发档案 `output/development-profile`，不碰正式数据；Work 模式，只读权限，测试工作区放三个小文本文件；模型 DeepSeek（负责人在开发档案里配置）。基于 PR #99 的分支，包含本 PR 全部改动。每一步都对照开发档案里的聊天历史、会话记录（`transcript.jsonl` 与 `snapshot.json`）和运行检查点核对。

| 场景 | 操作 | 结果 |
|---|---|---|
| 普通排队 | 运行中发一条消息，不点“立即发送” | 通过：运行结束后作为下一条消息发出，回复按它的要求用了表格 |
| 立即发送 | 多步读文件任务进行中，排队一条补充并点“立即发送” | 通过：下一次模型请求前写进聊天历史（带 `runInsertion`：运行、修订 1、顺序 1、所属回复）和会话记录（原文）；检查点保存了交付凭据；模型最终总结按补充开头写了“已收到补充” |
| 编辑后发送 | 排队 A，编辑成 B，再“立即发送” | 通过：插入的是编辑后的 B，模型按 B 收尾 |
| 连续插入 | B 之后再插入 C | 通过：B、C 在聊天历史与会话记录里顺序为 1、2 |
| 及时撤回 | 点“立即发送”后立刻点“撤回插入” | 通过：条目回到普通排队，运行结束后作为下一条消息发出 |
| 撤回太晚 | 运行已经取走后再点“撤回插入” | 契约正确：已插入的不能撤回，条目照常进入运行。但界面没有任何提示，见下文问题 2 |
| 会话记录丢失后补齐 | 关闭应用，从会话记录（含快照）里删掉已插入的 C，模拟写入没落盘；重启后发新消息 | 通过：新运行开始前，C 按原文、带运行编号补回会话记录，排在新消息前面，且只有一条 |

### 实机发现的问题（界面，留给过程流气泡 PR 3）

> 2026-11-19：问题 1、2、3 已在过程流气泡 PR 中修复并实机验证，见[验证报告](queue-insert-bubble-progress.md)。
