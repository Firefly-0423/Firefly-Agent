**目标：** 运行中插入的补充交给模型时，套上固定的中文说明，告诉模型这是用户在执行过程中补充的内容，并按负责人定的方式处理。
**保持不变：**
- 聊天历史、会话记录、记忆来源里一律是用户原文；
- 消息角色仍是 `user`；
- 仍只在 Work、Code 模式，带附件的消息不能插入；
- 会话记录的结构和版本不变。

## 负责人已定

- 模板采用简洁版（方案 A）：
  ```
  【运行中补充】用户在你执行任务的过程中补充了以下内容：
  <原文>
  请先检查已经完成的部分是否需要按这条补充调整，没有问题就补全之前的工作，然后接着做。
  ```
- 排查用的“渲染端提供上下文”开关（`FIREFLY_TRANSCRIPT_CONTEXT_SOURCE=renderer`）本 PR 不支持加框。这个模式下上下文来自渲染端，插入不会套说明；要支持，需要主进程另外从可信记录补投影。

## 契约

1. **加框只发生在两个边界：**
   - 已交付的插入进入运行循环时（`agent-loop.ts`）；
   - 会话记录物化成上下文时（`conversation-transcript-context.ts`）。

   普通路径、默认记忆、临时会话、压缩和摘要的输入都经过这两处。不按正文前缀判断“是否已经加过”；检查点存的是框好的文本，恢复时原样使用。
2. **会话记录怎么认出插入：** `user` 条目带非空 `runId`，就是插入，值为它插入的那次运行。字段注释写明这个字段专用于插入（`conversation-transcript-types.ts`）。
3. **四个写入口都写 `runId` 并比较：**
   - 普通拉取器的端口；
   - 默认记忆适配器；
   - 跨运行对账；
   - 首次历史回填。

   普通拉取器遇到同一轮次已有的条目，正文或 `runId` 对不上，就判为冲突，不可重试。
4. **旧数据：** #97 之前没有 `runId` 的插入条目当普通用户消息处理，不补框，不迁移。
5. **编辑：** 重新生成（`keep_user`）保留原插入的框；编辑（`replace_user`）后的新内容不套这个模板，在页面接回运行的 PR 里另定。
