# 运行中插入的补充可能丢失或被半截重放

状态：修复已提 PR（#96，施工包 1–7；真机造障未测）

日期：2026-11-16 至 2026-11-17

## 现象

Work、Code 运行中，用户把排队消息“立即发送”插入下一次模型请求。在下面两种情况下，插入的消息结果不对：

1. **一批里有一条写入失败。** 一次拉取取出 A、B、C，B 写入失败，整批被拒绝。A 其实已经写进去了，却没有交给运行，也没有写进检查点。运行在这里失败结束，A 的补充就丢了。
2. **会话记录写成了，聊天历史没写成。** 原顺序是先写会话记录、再提交聊天历史。中间失败时，会话记录里留下一条聊天历史里没有的用户消息，下一次运行会把它当成上下文重放。

## 根因

- `src/main/agent/runtime/pending-adjustment.ts` 原先先写会话记录，后提交聊天历史；任何一步失败，整次拉取都会 reject。
- `src/main/agent/memory-runtime/conversation-transcript-adapter.ts` 的 `commitRunAdjustment` 在默认记忆路径下也是同样的顺序，最后一步才提交聊天历史。
- 运行检查点不记录哪些插入已经交付；运行失败后，新运行也不会补齐只进了聊天历史的插入。

## 修复（#96）

1. 聊天历史的用户消息新增可选字段 `runInsertion`，只由主进程写入；检查点随消息保存交付凭据。持久化改动经负责人在 #96 批准。
2. 拉取结果改为 `{ delivered, blocked? }`：
   - 已完成的前缀先交给运行，并写进检查点；
   - 卡住的那条可以重试时，在下一次模型请求前有限重试；
   - 不能重试或重试用尽时，运行以“插话提交失败”结束，不会带着没生效的补充继续。
3. 普通路径和默认记忆路径都改为先提交聊天历史、再写会话记录。默认记忆路径把整个过程放在会话记录的同一次排队写入里完成；写失败后能在本次运行内按实际写入进度恢复，聊天历史和来源凭据都不会重复提交。
4. 新运行开始前，把之前运行里“已进聊天历史、会话记录缺失”的插入，按聊天历史顺序补进会话记录。

详见 [施工计划](../superpowers/plans/queue-insert-commit.md) 与 [验证报告](../superpowers/plans/queue-insert-commit-progress.md)。
