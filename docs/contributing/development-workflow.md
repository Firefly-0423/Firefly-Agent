# Firefly 开发流程

状态：流程规范
适用：1.2.0 起的全部开发（`dev/firefly-1.2.0` 及之后的分支）

本文规定一项改动从提出到合并的全过程：先写什么文档、怎么拆施工、测试写到什么程度、一个 PR 多大。工作约定和测试断言写法见仓库根目录 `AGENTS.md`，本文不重复，只在需要时引用。

## 1. 总流程

```
Issue（问题或需求）
  → 设计 / 规格（需要时）          docs/design/ 或 docs/superpowers/specs/
  → 施工计划（拆成施工包和任务）    docs/superpowers/plans/
  → 施工进度（每完成一小步就更新）  与计划同目录的 *-progress.md
  → 每个施工包一个 PR
  → 验收清单全部勾完 → 计划状态改为“已完成”
```

小改动（不改变其他模块依赖的行为、没有新状态或持久化格式、容易回退）可以跳过设计和计划，直接 Issue → PR。判断标准见 §6。

## 2. 文档类型与位置

| 类型 | 目录 | 什么时候写 | 第一行状态 |
|---|---|---|---|
| 设计 | `docs/design/` | 跨模块、要权衡多个方案的改动 | `状态：设计提案` / `状态：已定稿` |
| 规格 | `docs/superpowers/specs/` | 契约、接口、数据格式需要逐条定下来时 | `状态：设计规格（待审）` / `状态：已批准` |
| 施工计划 | `docs/superpowers/plans/` | 设计或规格定稿后，开始写代码前 | `状态：待施工` / `施工中` / `已完成` |
| 施工进度 | 同上，`<计划名>-progress.md` | 计划开工即建，跨会话或换人时的交接入口 | `状态：施工中（第 N 包）` |
| 已知问题 | `docs/internal-issue/` | 发现问题但暂不修，或修复需要先写调查报告 | `状态：待修复` / `已修复` |
| 参考资料 | `docs/references/` | 厂商错误码、外部协议等长期查阅的资料 | `状态：参考资料（核验日期 YYYY-MM-DD）` |
| 用户文档 | `docs/user-guide/` | 用户需要按步骤操作的功能 | `状态：用户文档` |
| 贡献文档 | `docs/contributing/` | 开发流程、某类贡献的专门规则 | `状态：流程规范` |

命名：`YYYY-MM-DD-英文短名.md`，日期取首次提交那天；用户文档和参考资料可以不带日期。正文用简体中文，代码标识符照原样。

## 3. 施工计划怎么写

一份计划要让另一个人（或另一个智能体）不问问题就能接着施工。固定结构：

```markdown
# 〈主题〉施工计划

状态：待施工
规格：docs/superpowers/specs/〈对应规格〉.md（没有规格时写“无，见 Issue #N”）

**目标：** 一两句话，用户能得到什么。
**架构：** 一段话，核心做法和与现有模块的衔接。
**不改的东西：** 明确列出保持不变的行为、契约、数据格式。

## 全局约束
- 例：不新增运行时依赖；不读取 1.1.x 用户数据；Chat / Work / Code 三种模式都要覆盖。

## 文件清单
### 新建
### 修改

## 施工包
（每个施工包 = 一个 PR，见 §5）

### 施工包 A：〈名称〉
**改动文件：** …
**任务：**
- [ ] A1 〈一个可以独立验证的小步骤〉
  - 先写的测试：`〈测试文件〉`：〈输入条件〉→〈断言什么，含不该发生的副作用〉
  - 实现：〈改哪里〉
  - 验证：`〈实际存在的命令〉`
- [ ] A2 …
**验收：** 〈这一包合并前必须满足的条件〉
**回退：** 〈出问题时 revert 哪个提交，会不会留下数据〉

## 验收清单（全量）
- [ ] …（包括真机验证：打包版里怎么操作、看到什么算通过）

## 回滚方案
## 待负责人决定
```

要点：

- **任务的粒度**：一个任务能在一次会话里完成，并且有自己的测试。拿不准时拆小。
- **先测试后实现**：每个任务先写失败的测试，再写实现，再跑验证命令（`AGENTS.md` 的测试驱动要求）。
- **写死证据**：涉及现有代码的地方写文件路径和行号或符号名，不写“大概在某处”。
- **不在计划里留讨论**：已定的取舍直接写结论；没定的放进“待负责人决定”，开工前清空。

## 4. 施工进度文档

施工进度是交接入口。每完成一个任务就更新，内容：

1. **当前状态**：做到第几包第几个任务，工作区是否干净，分支和最新提交。
2. **已完成项**：每项写改了什么、提交号、跑过的验证命令和结果（通过数）。
3. **未完成项**：剩下的任务和已知问题。
4. **验证记录**：全量测试、类型检查、构建、真机验证各自的最后一次结果和日期。
5. **偏离计划的地方**：实际做法和计划不一样时，写明原因；影响后续施工包的，同步改计划。

换会话、换人或换智能体时，先读进度文档，再读计划，不要从头重做。

## 5. PR 颗粒度

### 5.1 一个 PR 一个施工包

- 一个 PR 只做一件能独立验证、独立回退的事：一个修复、一个功能的一包、一次重命名。
- 不夹带无关的格式化、重构、依赖升级或顺手修的其他问题；顺手发现的问题另开 Issue 或另提 PR。
- 版本号变更单独一个 PR（`chore(版本号): …`），不和功能混在一起。
- 纯格式问题（如换行符）单独一个 PR，并在说明里写明“无行为变化”。

### 5.2 规模参考

| 规模 | 参考 | 处理 |
|---|---|---|
| 小 | 1–5 个文件，几十到两百行 | 常规 |
| 中 | 6–15 个文件，几百行 | 说明里按文件分组讲清楚 |
| 大 | 超过 15 个文件或上千行（不含测试和生成文件） | 先想能不能拆；拆不开（如一次跨模块的契约收紧）就在说明里写为什么不拆，并附完整链路的验证 |

测试代码不计入规模，但测试要和实现在同一个 PR 里。

### 5.3 标题与提交

- 标题：`类型(范围): 描述`。类型用 `feat` / `fix` / `refactor` / `perf` / `docs` / `test` / `chore` / `style`；范围写模块（如 `模型`、`权限`、`记忆`、`插件`、`渠道`、`设置`，或英文模块名）；描述写做了什么，不写“修改了一些问题”。中文或英文都可以，一个 PR 内保持一致。
- 每个施工包可以有多个提交，但合并后要能按包整体 revert。
- 分支名用 Firefly 的词：`feat/…`、`fix/…`、`docs/…`、`dev/firefly-…`。
- 提交说明和 PR 说明不写与改动无关的背景。

### 5.4 PR 说明

使用 `.github/pull_request_template.md`：相关 Issue、变更说明（为什么改、改了什么）、测试（实际运行的命令、范围、结果、未验证项）、Checklist。跨模块改动要验证实际运行时经过的完整链路，不只验证单个函数。

### 5.5 合并前

- CI（`.github/workflows/test.yml`）通过。
- 审查按 `AGENTS.md` 的“审查”一节进行；同一个 PR 最多三轮“审查 → 修改”，三轮后仍有分歧就停下来重新讨论方案。
- 涉及界面或运行行为的改动，在打包版或开发版里实际操作过一遍，PR 里写操作步骤和结果。

## 6. 哪些改动要先开 Issue 讨论

问三个问题，任何一个答“是”，先开 Issue，方向确认后再写代码：

1. 会改变**其他模块依赖的行为**吗（不只是内部实现）？
2. 会引入**新的状态、生命周期或持久化格式**吗？
3. 合并后**很难回退**吗（数据格式、外部契约、安全边界）？

核心模块清单（这些模块的行为、契约和安全边界改动一律先讨论）：

| 模块 | 代码位置 | 先讨论 | 可直接 PR |
|---|---|---|---|
| 运行循环 | `src/main/agent/loop/`、`src/main/agent/runtime/`（`firefly-agent.ts`、`chat-loop.ts`）、`src/main/features/chat/agui-bridge.ts` | 运行终态与结算、取消 / 超时 / 错误的区分、重试策略、事件顺序、适配层接口 | 不改语义的修复、日志 |
| 记忆 | `src/main/memory/`、`src/main/agent/memory-runtime/` | 判定与冲突策略、存储结构、注入逻辑 | 导入导出修复、记忆管理界面 |
| 插件 | `src/plugins/`、`src/main/features/plugins/host/`、`plugin-sdk/` | 清单字段、能力与权限、生命周期、隔离与安全边界 | 示例插件、SDK 文档、不改契约的修复 |
| 工具 | `src/main/agent/tools/` | 新增内置工具（尤其写文件、执行命令、联网）、各模式的工具暴露、参数和返回格式、写入防护 | 工具说明文案、不改行为的修复 |
| 上下文 | `build-options.ts`、`context-manager.ts`、`prompt-layers.ts`、`src/main/base/runtime-policy/` | 提示词分层、压缩与裁剪、Token 预算、各来源的注入顺序 | 上下文查看界面、注入格式修复 |
| 权限 | `src/main/platform/permission/`、`src/main/agent/sandbox/` | 任何**放宽**权限的改动、审批流语义、沙箱和命令执行规则 | 审批卡片界面和文案、不改安全语义的修复 |
| 调度 | `src/main/features/scheduler/` | 错过任务的处理、下次触发时间规则、插件任务的所有权和授权、存储格式 | 不改语义的修复（如时区计算）、调度界面 |
| 渠道 | `src/main/features/channels/` | 外部消息进入的模式和工具范围、账号与会话绑定、审批相关 | 单个适配器的修复 |
| 启动与数据 | `src/main/base/identity/`、`src/main/base/storage/`、`src/main/platform/updater/` | 数据目录、单实例、安装身份、更新、资源路径 | 日志和诊断 |

## 7. 测试

- 断言写法按 `AGENTS.md`“测试断言写法”的 12 条。
- 测试文件与被测文件同目录，命名 `*.test.ts`；跨进程或需要真实文件的测试放在临时目录里做，结束后清理。
- 验证顺序：最近的测试 → 所在模块 → `npm run build:main` / `npm run build:preload` / `npm run check:renderer` → 全量 `npm test`（需要 `FIREFLY_TEST_BASH` 指向 Git Bash）。
- 新增原生辅助程序或打包相关的改动，还要在打包版里验证。
- 平台限制导致跑不了的断言，用显式跳过并写明原因。

## 8. 完成的定义

一项施工算完成，需要同时满足：

- 计划里所有施工包已合并，验收清单全部勾完；
- 进度文档的最后验证记录包含全量测试、类型检查、构建和真机验证；
- 计划和进度文档的状态改为“已完成”，未做的项移到新的 Issue 或已知问题文档。
