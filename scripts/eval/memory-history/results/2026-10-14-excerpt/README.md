# 2026-10-14 留存评测（第三批）：超长会话的证据能不能送达

> **订正（评审之后，务必先读）。** 本批把长会话做成了 450 条消息的**一份**文档，这在生产里不成立：
> - 读取端把一份文档限制在 **128 条消息**以内（`history-repository.ts` 的 `list(d.messages, 128)`），450 条的文档入不了库；前两批的长会话（160–190 条消息）同样超过这个上限。
> - 原生历史按"一条用户消息及其后的助手/工具消息"分组，**一组一份文档**（`firefly-history-reader.ts` 的 `records`），所以"会话总长超过 6000 字"并不等于"会被整段丢弃"，真正受预算影响的是**单份文档**。
>
> 因此下面的数字只能说明：**摘录选择对"由许多中等长度消息组成、总长超预算"的文档有效**；它不是对真实文档形状的测量。真实的超限文档更可能是消息数不多、单条很长（例如长工具输出）的一轮，这种文档里连最佳窗口也可能放不下。真实收益要用实际文档的统计来判断：单份文档的字符数分布、超限比例、以及查询因预算被丢弃的次数。


本批回答一个问题：**命中了一个超过 6000 字的会话，里面的那句话最终能不能到模型手里？** 前两批只量排序名次；生产里命中之后还有摘录预算（`maxExcerptChars` 6000、`maxTotalChars` 16000），超预算的会话会被整段丢弃，名次再高也送不到模型。

设计见 `output/memory-design-window-evidence.md`（本地设计稿）。本批只量化问题和"只对超长会话改为返回最佳窗口"这一个方案，**产品行为没有改变**：`selectExcerpt` 和排序结果里的最佳窗口下标是新增的纯函数与字段，尚未被检索流程使用。

## 方法

- 数据：同一份合成语料，只把 16 个长会话从约 160 轮拉到 450 轮以上（`--long-turns 450`，全部超过 6000 字预算）。多出来的填充句由**按会话独立的随机数**生成，分布在关键句前后，所以改变 `--long-turns` **不会改变其余 234 个会话和全部查询**（有单测守护）；`--long-turns 0` 时数据与之前逐字节相同。这一点是评审指出的：最初的实现让长会话多消耗共享随机数，连带改变了所有干扰会话，对照就混入了语料差异，已改正并重跑，下面是重跑后的数字。
- 打包：`packEvidence`（`metrics.mjs`）**复刻仓库的预算循环**：按名次逐个放入，整份超过单份上限或累计超过总上限就跳过。两种策略：
  - `整份或丢弃`：生产现状，超预算的会话丢弃；
  - `摘录（仅超长）`：只对**单份就超过 `maxExcerptChars` 的会话**，用 `selectExcerpt` 取最佳窗口（2 轮）加上前后各 1 个窗口的上下文；放得下单份上限的会话仍整份返回，只是总预算不够的会话照旧跳过（评审指出最初的实现会把这类会话也切成摘录，已改正并有单测）。
- 指标：**证据召回**——送达的消息里是否包含关键句（needle）所在的那条消息。只对 needle 类题计算（dev 12 题，holdout 4 题）。
- 配置：窗口 2 轮、上下文 1 个窗口、预算为 `DEFAULT_HISTORY_SETTINGS`。上下文窗口数没有调过，直接用设计稿里的默认值。

## 结果

| 证据召回 | 整份或丢弃 | 摘录（仅超长） | 平均送达字数（整份 → 摘录） |
|---|---|---|---|
| dev，needle 12 题（词法 / 混合 / 混合 + 新近度） | 0% / 0% / 0% | 83% / 83% / 83% | 168 → 441 / 137 → 483 / 134 → 485 |
| holdout，needle 4 题（同上） | 0% / 0% / 0% | 75% / 75% / 75% | 105 → 437 / 51 → 523 / 51 → 515 |

排序名次本身与前两批一致：整体 Hit@1 dev 词法 51%、混合 43%、混合 + 新近度 46%，holdout 55% / 55% / 57%，见各 `.md`。needle 类 Hit@1（dev）：词法 67%，混合 17%，混合 + 新近度 25%。"摘录"能不能送达看的是前 8 名里有没有这个会话，且最佳窗口是不是关键句所在的窗口，所以摘录后的送达率（83%）高于混合的 Hit@1。

说明：`.md` 报告里的表头文字是运行时写死的旧措辞"只对被丢弃的会话"，实际口径是"单份就超过上限的会话"；本语料里被丢弃的都是单份超限，两者在这里等价，后续运行的措辞已改。

## 读法，务必一起看

1. **"整份或丢弃 = 0%"是构造出来的。** 我把所有长会话都做成了超过 6000 字，所以必然全部被丢弃。它证明的是"会话一旦超过预算就拿不到"这个机制，**不说明真实使用里有多少会话超过 6000 字**——这一点我没有真实数据，需要从真实（脱敏）会话里统计长度分布，才能知道这个问题的实际规模。
2. **样本很小**：dev 12 题、holdout 4 题，区间会很宽（4 题里 3 题是 75%，差一题就是 50% 或 100%）。方向一致，不能说精确提升了多少。
3. **留出集并不新**：查询文本没有变，只有语料（长会话长度和填充）变了，它与前两批的留出集看的是同样的问题。这一批只在 dev 上做了配置选择（实际上没有调参），holdout 冻结配置只跑了一次；需要真正的新留出集时，必须新写查询。
4. **打包是对仓库预算循环的复刻，不是仓库本身。** 授权、来源校验、证据外壳的字符数都没有计入；证据外壳会让真实预算更紧，所以这里的送达率偏乐观。
5. **关键句很短，窗口很小**（平均约 440–500 字）。真实对话里单条消息可能很长，一个窗口放不下就仍然丢弃（设计稿里"不截断消息"的取舍）。
6. 向量路线命中、词法没命中的超长会话没有"最佳窗口"，第一版仍然拿不到，需要窗口级向量。
