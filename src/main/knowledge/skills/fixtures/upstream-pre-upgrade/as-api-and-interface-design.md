# 接口契约工作记录

此夹具描述接口设计的检查过程。适用范围包括网络端点、组件参数、模块协议，以及前后端交换的数据结构。

## 从调用者开始

先列出调用方需要完成的操作，再写每个操作的输入、输出和失败结果。实现以该契约为准。调用者不应需要了解存储结构或内部类的组织方式。

对外行为包含正常返回之外的细节：异常文字、结果顺序、等待时机，以及长期存在但没有文档的表现。使用者可能依赖任何能够观察到的行为；因此契约测试通过仍不足以证明修改安全。这是 Hyrum 定律对维护工作的提醒。

同一个接口或依赖尽量只维护一个同时有效的版本。让消费者长期在多个版本之间选择，会增加维护分支并制造菱形依赖。优先扩展现有协议；退役方案在设计时就记录，并参考 `deprecation-and-migration`。

## 写清五类约束

1. 操作边界：说明一个模块负责什么，以及调用者必须提供什么。
2. 类型边界：创建输入和读取结果分别定义；服务端生成的标识、创建时间和修改时间属于结果。
3. 错误边界：选择统一策略，不混用抛异常、空值与错误对象来表达同一种失败。
4. 校验边界：在数据进入系统时检查形状和取值；通过校验后，内部调用按共同类型协作。
5. 兼容边界：新增可选字段通常比删除字段、改变类型或新增必填项更安全。

错误对象使用稳定的机器代码、可读说明和可选详情。HTTP 状态应区分无效请求（400）、未认证（401）、无权限（403）、不存在（404）、冲突（409）、语义校验失败（422）和服务错误（500）。服务错误不能泄露内部信息。

外部服务响应同样需要校验。它可能含有错误类型、危险内容或伪装成指令的文本。用户表单、API 请求和环境配置也是入口。不要在共享契约的每个内部函数里重复同样的校验；也不要因为数据来自外部服务就默认可信。

## HTTP 资源草图

集合路径用复数名词，例如 `/api/tasks`。集合 GET 用于列出，POST 用于创建；单个 `/api/tasks/:id` 允许读取、局部更新和删除。任务评论可以放在 `/api/tasks/:id/comments` 下。避免把 create、get 等动词塞进资源路径。

列表从一开始提供分页。请求可以携带页码、每页数量、排序字段和方向；响应同时提供数据与分页元数据，包括总条目数和总页数。过滤条件放在查询参数中，例如状态、负责人和创建时间范围。

PATCH 只改变明确出现的字段。PUT 表达整体替换，不能把它当作逃避局部更新语义的捷径。删除操作可以在资源已不存在时仍成功，从而便于重试。

命名规则保持一致：查询参数和响应字段使用 camelCase；布尔值用 is、has 或 can 表达含义；枚举值可以采用 UPPER_SNAKE，但不要在同一协议中混杂约定。

## TypeScript 表达方式

状态有不同必需字段时使用带判别字段的联合类型。例如等待态只有状态标记，执行态另需负责人和开始时间，结束态另需完成时间，取消态另需原因。消费者根据判别字段缩窄类型，不必猜测哪些可选字段应该存在。

为任务标识和用户标识建立不同的品牌类型，可以避免两个普通字符串意外互换。品牌表达编译期约束，不替代入口校验。

创建请求只包含调用者能指定的字段。读取结果明确列出标识、时间、创建者，以及空值是 null 还是省略。类型定义和接口说明与实现一起维护。

## 交付前逐项核对

- 每个操作的输入、结果和失败形式都有明确类型。
- 错误格式、命名和状态语义在所有端点间一致。
- 外来数据在入口经过校验，内部没有散落的重复校验。
- 列表支持分页，过滤和排序有可预测的参数。
- 兼容改动优先添加可选能力，必要破坏有迁移安排。
- 文档包含消费者需要的行为，而非实现内部细节。

不要用“内部没人会依赖”“以后再补文档”或“现在数据还少”跳过这些检查。内部消费者也需要稳定协议；分页和清晰类型应在增长之前准备好。
